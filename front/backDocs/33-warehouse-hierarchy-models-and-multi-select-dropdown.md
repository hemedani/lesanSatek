# Warehouse Classification Hierarchy (WareType / WareClass / WareGroup / WareModel / Ware) + Multi-Select Dropdown for M:N Relations

> Scope: `back/models/ware.ts`, `back/models/wareModel.ts`, `back/models/wareType.ts`, `back/models/wareClass.ts`, `back/models/wareGroup.ts` + the corresponding `back/src/*` actions + the frontend dropdown gap.
>
> Target audience: frontend developers implementing the admin CRUD forms and the new multi-select component.

---

## 1. Big Picture — The 4‑Level Classification Hierarchy

The warehouse domain is organized as a strict 4‑level classification tree, plus a concrete product node at the bottom:

```
WareType            (level 1 — top-level category)        e.g. "تجهیزات آزمایشگاهی" / Laboratory Equipment
  └── WareClass     (level 2 — sub-type of a WareType)    e.g. "هماتولوژی" / Hematology
        └── WareGroup (level 3 — sub-type of WareType)    e.g. "کیت" / Kit        ← M:N with WareClass
              └── WareModel (level 4 — specific model)    e.g. "کیت TSH پیشرفته" / Advanced TSH Kit
                    └── Ware  (concrete product)          e.g. "کیت TSH پیشرفته ZistShimi"
                          └── Stuff  (store inventory of that product, with price/qty)
```

Key facts that shape everything below:

| Model | Level | Parent relations (required?) | M:N? | Used as SKU-ish ref? |
|-------|-------|------------------------------|------|----------------------|
| `WareType` | 1 | — | No | No |
| `WareClass` | 2 | `wareType` (required) | **Yes, via `WareGroup.wareClasses`** | No |
| `WareGroup` | 3 | `wareType` (required) | **Yes — holds `wareClasses` M:N array** | No |
| `WareModel` | 4 | `wareType`, `wareClass`, `wareGroup` (all required, **single**) | No | **Yes** — `PurchasingRequest.wareModel`, `Inventory.wareModel`, `Consumption.wareModel` store `wareModelId`/`wareModelName` |
| `Ware` | product | `wareType`, `wareClass`, `wareGroup`, `wareModel` (all required, **single**) + `manufacturer` (optional) | No | No — but `Stuff`/`StockMovement`/`Consumption` reference it optionally |

> **Important for the frontend:** The **only M:N relationship in this whole hierarchy is `WareGroup ↔ WareClass`**. Every other edge is a *single* relation. So when the user says "some ware models are m‑m relations", they mean **WareGroup** (which links to many WareClass records) — **not** the `WareModel` entity itself. `WareModel` belongs to exactly **one** WareType, one WareClass, one WareGroup.
>
> There is a second M:N elsewhere: `Store.wareTypes` (`store.ts`), which needs the **same** multi-select component.

## 2. Shared Conventions Across All Five Models

- **Pure fields** are only `name`, `enName`, plus the auto `createdAt`/`updatedAt` from `createUpdateAt` (`@lib`). `Ware` adds more pure fields.
- **Creator**: every model has a required single `creator` relation to `user`. Lesan auto-manages the reverse side.
- **Text index**: each model creates a `$text` index on `name` + `enName` (`createIndex.indexSpec`). This powers the `search` full-text filter in `gets`.
- **Denormalized single relations**: Lesan **embeds** single-type relations (WareType/WareClass/WareGroup/WareModel inside a Ware doc) as inline subdocuments. That means MongoDB queries can filter directly on `"wareType._id"`, `"wareClass._id"`, etc. with zero joins. **Never** duplicate `xxxId`/`xxxName` pure fields for these — the relation already lives in the same document.
- **Excludes** (in `models/excludes.ts`): all four hierarchy models + ware exclude only `createdAt`/`updatedAt` when embedded. `ware_excludes` additionally drops `price` and `orderedNumber` (avoids leaking pricing into nested relation payloads).
- **Auth** on all write actions: `grantAccess([{ roles: ["Manager", "Admin"] }])`. Reads (`get`/`gets`/`count`) are open to any authenticated user with an `activeRoleId`.

### 3.1 `WareType` — Level 1

`models/wareType.ts`

**Pure fields**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | `string` | yes | Persian name, e.g. `"تجهیزات آزمایشگاهی"` |
| `enName` | `string?` | no | English name, e.g. `"Laboratory Equipment"` |
| `createdAt` / `updatedAt` | `Date` | auto | from `createUpdateAt` |

**Relations** — only one defined here:

| Relation | Type | Optional | Reverse on target (auto) |
|----------|------|----------|--------------------------|
| `creator` | single (`user`) | no | — |
| *(implicit)* | | | `wareClasses`, `wareGroups`, `wareModels`, `wares`, `stuffs` — all **auto-generated by Lesan** from child models. Do NOT re-declare on WareType. |

**Actions** (`src/wareType/`): `add`, `get`, `gets`, `update`, `remove`, `count` — **no `updateRelations`** (it has no mutable relations other than `creator`).

**Example document**
```json
{
  "_id": "64f...",
  "name": "تجهیزات آزمایشگاهی",
  "enName": "Laboratory Equipment",
  "createdAt": "2024-01-01T00:00:00Z",
  "updatedAt": "2024-01-01T00:00:00Z"
}
```

**gets filter:** `search` (full-text on name/enName) + `pagination` + `sortBy` (`createdAt | updatedAt | name`). No hierarchy filter (nothing above it).

**Deletion:** `remove` uses `wareGroup`-style safe `deleteOne` (see §6). Because WareClasses/WareGroups/WareModels/Wares/Stuffs all reverse-reference it, deleting a WareType is **blocked** while children exist unless `hardCascade: true` is passed.

### 3.3 `WareGroup` — Level 3 ⭐ M:N owner

`models/wareGroup.ts`

**Pure fields**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | `string` | yes | Persian name, e.g. `"کیت"` |
| `enName` | `string?` | no | English name |
| `createdAt` / `updatedAt` | `Date` | auto | |

**Relations**

| Relation | Type | Optional | Reverse on target (auto) | Notes |
|----------|------|----------|--------------------------|-------|
| `creator` | single (`user`) | no | — | |
| `wareType` | single (`wareType`) | no | `wareType.wareGroups` (limit 50, sort `_id` desc) | Every group belongs to exactly one top-level type |
| `wareClasses` | **multiple** (`wareClass[]`) | **yes** | `wareClass.wareGroups` (multiple, **no limit, no sort**) | ⭐ **THE M:N relationship.** Defined here, no join table. |

```typescript
// models/wareGroup.ts (the M:N, lines 60–72)
wareClasses: {
  schemaName: "wareClass",
  type: "multiple",
  optional: true,
  limit: 50,
  excludes: wareClass_excludes,
  sort: { field: "_id", order: "desc" },
  relatedRelations: {
    wareGroups: { type: "multiple" },   // auto reverse on WareClass
  },
},
```

**Actions** (`src/wareGroup/`): `add`, `get`, `gets`, `update`, `updateRelations`, `remove`, `count`.

**`wareGroup.add` validator / fn** (`add/add.val.ts`, `add/add.fn.ts`):
```typescript
set: object({
  ...activeRoleMixin,
  ...wareGroup_pure,          // name, enName (+ created/updatedAt)
  wareTypeId: objectIdValidation,                       // required, single
  wareClassIds: optional(array(objectIdValidation)),    // ⭐ M:N, array
})
```
`add.fn.ts` maps `wareClassIds` → `relations.wareClasses = { _ids: [...], relatedRelations: { wareGroups: true } }`. **`wareClassIds` is the ONLY array-valued relation field in the whole hierarchy.**

**`wareGroup.updateRelations` validator / fn** (`updateRelations/updateRelations.val.ts`, `.fn.ts`):
```typescript
set: object({
  ...activeRoleMixin,
  _id: objectIdValidation,
  wareTypeId: optional(objectIdValidation),
  wareClassIds: optional(array(objectIdValidation)),   // ⭐ M:N, array
})
```
The fn calls `addRelation` **twice** (once for `wareType`, once for `wareClasses`), each with `replace: true` — meaning whatever you send **replaces the whole current set** (the old `wareClasses` links are removed and the new ones added; Lesan also cleans the old reverse `wareClass.wareGroups` entries).

**gets filter** (`gets/gets.fn.ts`):
- `search` — full-text
- `wareTypeId` — `"wareType._id"`
- `wareClassId` — `"wareClasses._id"` (⚠️ single value; matches if the group contains that class. See §7 side effect about M:N filtering.)

| `enName` | `string?` | no | English name |
| `createdAt` / `updatedAt` | `Date` | auto | |

**Relations — all single, all required**

| Relation | Type | Optional | Reverse on target (auto) |
|----------|------|----------|--------------------------|
| `creator` | single (`user`) | no | — |
| `wareType` | single (`wareType`) | no | `wareType.wareModels` |

| `wareGroup` | single (`wareGroup`) | no | `wareGroup.wareModels` |
| *(implicit)* | | | `wares`, `stuffs` — auto from child models |

**Actions** (`src/wareModel/`): `add`, `get`, `gets`, `update`, `updateRelations`, `remove`, `count`.

⚠️ **Gotcha:** `wareModel.updateRelations` validator declares **only** `_id` (updateRelations.val.ts) — it exposes **no** `wareTypeId/wareClassId/wareGroupId`. **Deletion:** deleting a WareModel is blocked while `wares`/`stuffs` (or PurchasingRequest/Inventory references) reverse-reference it, unless `hardCascade: true`. In practice PRs snapshot `wareModelId`/`wareModelName` as **pure fields** too, so the *string* reference survives deletion even though the relation is dropped.

**`ware.gets`** — the richest filter set (`gets/gets.fn.ts`):
- Hierarchy: `wareModelId`, `wareClassId`, `wareGroupId`, `wareTypeId`, `manufacturerId` (single ObjectId matches on embedded docs)

## 4. Cross-Model Relation Map (the full picture)

```
WareType (level 1)
  ├── creator (User)
  ├── wareClasses (reverse, from wareClass.wareType)
  ├── wareGroups  (reverse, from wareGroup.wareType)
  ├── wareModels  (reverse, from wareModel.wareType)
  ├── wares       (reverse, from ware.wareType)
  └── stuffs      (reverse, from stuff.wareType)

WareClass (level 2)
  ├── creator (User)
  ├── wareType (WareType, single, required)
  ├── wareGroups (M:N reverse, from wareGroup.wareClasses)   ⭐
  ├── wareModels (reverse, from wareModel.wareClass)
  ├── wares      (reverse, from ware.wareClass)
  └── stuffs     (reverse, from stuff.wareClass)

WareGroup (level 3)
  ├── creator (User)
  ├── wareType   (WareType, single, required)
  ├── wareClasses (WareClass[], M:N, optional)               ⭐
  ├── wareModels (reverse, from wareModel.wareGroup)
  ├── wares      (reverse, from ware.wareGroup)
  └── stuffs     (reverse, from stuff.wareGroup)

WareModel (level 4)
  ├── creator (User)
  ├── wareType   (single, required)
  ├── wareClass  (single, required)
  ├── wareGroup  (single, required)
  ├── wares      (reverse, from ware.wareModel)
  └── stuffs     (reverse, from stuff.wareModel)

Ware (product)
  ├── creator (User)
  ├── manufacturer (single, optional)
  ├── wareType   (single, required)
  ├── wareClass  (single, required)
  ├── wareGroup  (single, required)
  ├── wareModel  (single, required)
  └── stuffs     (reverse, from stuff.ware)
```

Rules of thumb:
1. **The child defines the relation.** `wareClass` defines `wareType`; `wareGroup` defines `wareType` + `wareClasses`; `wareModel` defines its three parents; `ware` defines its four parents + manufacturer; `stuff` defines its five. **Never** declare the reverse on the parent (WareType/WareClass/etc. stay clean — Lesan embeds the reverse automatically).
2. **Only two array relations in the whole hierarchy**: `wareGroup.wareClasses` and (outside the hierarchy) `store.wareTypes`. Both need a multi-select in the frontend.
3. Everything else is single.

## 6. Deletion / Cascade Behavior (safe mode)

Every `remove` uses the same pattern (`hardCascade: hardCascade || false`):

```typescript
return await wareGroup.deleteOne({ filter: { _id: new ObjectId(_id) }, hardCascade: false });
```

- Deleting a **child** (e.g. WareGroup) automatically removes it from every parent's embedded reverse array (e.g. `wareClass.wareGroups`, `wareType.wareGroups`). No manual cleanup.
- Deleting a **parent** (e.g. WareType, or a WareClass that has WareGroups reverse-referencing it) is **blocked** while children still reference it. Lesan returns an error telling you to clear children first.
- `hardCascade: true` cascade-deletes children — dangerous, never used in the normal UI flow.

**Practical consequence for the WareGroup ↔ WareClass M:N:** a WareClass that still has WareGroups cannot be deleted until all its WareGroups are removed or unlinked (`updateRelations` with an empty `wareClassIds` array effectively unlinks). Conversely, deleting a WareGroup never touches the WareClass docs.

## 7. The M:N Relationship — Deep Dive & Side Effects

### 7.1 How it's stored

`WareGroup` documents physically hold an embedded `wareClasses` array of full WareClass subdocuments (limit 50, sorted `_id` desc):

```json
{
  "_id": "grp_kit",
  "name": "کیت",
  "enName": "Kit",
  "wareType": { "_id": "wt_lab", "name": "تجهیزات آزمایشگاهی" },
  "wareClasses": [
    { "_id": "cls_hem", "name": "هماتولوژی" },
    { "_id": "cls_chem", "name": "شیمی" }
  ]
}
```

The reverse side is a native NoSQL M:N: each `WareClass` document also embeds a `wareGroups` array (auto-managed by Lesan; defined with **no limit and no sort**).

### 7.2 Writing (add / updateRelations) side effects

- **`add` with `wareClassIds`**: inserts the WareGroup, then for each WareClass in the array, **appends** the group to that class's `wareGroups` reverse array (via `relatedRelations: { wareGroups: true }`).
- **`updateRelations` with `wareClassIds` + `replace: true`**: the **whole** existing `wareClasses` set is replaced. Lesan:
  1. removes the group from the `wareGroups` arrays of the **old** classes,
  2. adds it to the `wareGroups` arrays of the **new** classes.
  - ⚠️ Side effect: **any class you omit from `wareClassIds` is unlinked.** The client must always send the *complete* intended set, not a delta.
  - ⚠️ `replace: true` also applies to `wareType` in the same fn — omitting `wareTypeId` keeps the old type, but sending a different `wareTypeId` re-parents the group (both updateRelations calls run sequentially in the fn).

### 7.3 Query side effects

- `wareGroup.gets` filters with `wareClassId` → `$match: { "wareClasses._id": ObjectId }`. Because the array holds **many** classes, a single group **matches every one of its classes**. So in the process-scope / filter UIs, a group shows up under *each* of its class filters. This is correct M:N behavior but can surprise: the same group appears in multiple filtered lists.
- There is **no multi-value filter** (`$in`) exposed today. If you want "groups that belong to ANY of these N classes", the backend needs a new filter (e.g. `wareClassIds: array`) implemented as `"wareClasses._id": { $in: [...] }`. Out of scope until product asks for it.
- Because `wareGroup.gets` **requires** `wareTypeId`+`wareClassId` chain usage in the frontend (process-scope-fields.tsx), a group belonging to classes *outside* the currently-selected class will not appear — same as any single select. No change needed.

### 7.4 Downstream visibility of M:N

- **Process scoping** (`process.unit/wareType/wareClass/wareGroup/wareModel/ware`) uses single selects. A process scoped to a `WareGroup` implicitly covers all models of all classes that group belongs to. Document this in the admin UI ("گروه کالا" scope = all ردههای آن گروه).
- **Ware/WareModel** belong to exactly one WareGroup, so there is no ambiguity downstream — only the WareGroup itself is multi-class.
- **Store.wareTypes** (outside hierarchy) is the second M:N; the same multi-select component and the same `add`-accepts-array + `updateRelations`-replace semantics apply (`src/store/add/add.fn.ts` maps `wareTypeIds` → `relations.wareTypes`).

## 8. Frontend — Current State & the Multi-Select Gap

### 8.1 What exists today

Two dropdowns:

1. **`SearchSelect` / `FormSearchSelect`** (`front/src/components/form/form-search-select.tsx`) — the "nice single select". Built on `@base-ui/react/popover` + `cmdk` (Command). It:
   - holds a **single** `value: string`,
   - calls `fetcher(search?)` to load options (`SearchSelectOption = { _id, name, sublabel?, data? }`),
   - renders a checkmark on the selected item,
   - shows `displayLabel` or the selected option's `name` in the trigger,
   - **cannot** represent multiple selections: the trigger renders a single label, `Command.Item onSelect` replaces the value, and there's a single `CheckIcon`.

2. **`Select` / `FormSelect`** (`front/src/components/ui/select.tsx`, `form-select.tsx`) — plain single select from `@base-ui/react/select`. Base UI `Select` is **single-select only**; it has no multiple API.

### 8.2 Where the M:N is currently broken/absent in the UI

- **`front/src/app/admin/ware-groups/ware-groups-client.tsx`** is the canonical broken spot:
  - The `wareGroupSchema` (zod) only validates `{ name, enName, wareTypeId }` — **no `wareClassIds`**.
  - `add()` is called **without** `wareClassIds`, even though the backend accepts it (`wareGroup.add`).
  - `openEdit` resets only name/enName/wareTypeId; on save it calls `update` (pure fields only) and **never calls `updateRelations`** — so the `wareClasses` M:N links can be created via the API but **cannot be set or edited from this admin page at all**.
  - The list view *displays* `item.wareClasses` badges (lines 185–193), so the data is visible but not editable. → **Feature gap.**
- **`front/src/app/admin/processes/add/page.tsx` + `process-scope-fields.tsx`** — process scope uses single selects for `wareType/wareClass/wareGroup/wareModel/ware` and is **fine as-is** (those are single relations). Do **not** turn these into multi-selects.
- **`front/src/app/admin/ware-classes/ware-classes-client.tsx`** — WareClass has no M:N of its own, single `wareType` select is correct.
- **`front/src/app/admin/ware-models/ware-models-client.tsx`** — WareModel relations are single; single selects correct.
- **Store forms** (wherever Store.wareTypes is edited) — same gap as ware-groups; needs the multi-select once built.

> Bottom line: **multi-select is needed for the two M:N relations: `WareGroup.wareClasses` and `Store.wareTypes`.** Everything else stays single-select.

### 8.3 Proposed component: `SearchMultiSelect` / `FormSearchMultiSelect`

Add a multi variant modeled directly on `SearchSelect` (Popover + Command + fetcher), so it reuses the existing search/async-loading pattern and RTL styling:

- Props:
  ```typescript
  interface SearchMultiSelectOption { _id: string; name: string; sublabel?: string; data?: Record<string, unknown> }
  // SearchMultiSelect
  { value: string[]; onChange: (values: string[]) => void; fetcher; ... }
  // FormSearchMultiSelect (RHF wrapper)
  { control; name; label; fetcher; required?; onValueChange?: (values: string[]) => void }
  ```
- **Behavior:**
  - `Command.Item onSelect` **toggles** the id in/out of `value` (instead of replacing).
  - Render a `CheckIcon` on every item whose `_id` is in `value`.

### 8.4 Side effects & edge cases to handle (checklist)

1. **`replace: true` full-set semantics** — the edit form must initialize `wareClassIds` from the *current* document and always submit the complete set. A user un-ticking one checkbox must send the remaining list (backed up by the same behavior the backend expects).
2. **Option label resolution for already-selected ids** — the loaded options page may not contain an already-selected class (pagination/limit 50, or the option set changed). The trigger chips need a `nameMap` (id → name), built from:
   - the parent page's preloaded data (list items already include `wareClasses`),
   - `onSelectData` tracking during selection (same `track()` pattern as process-scope-fields),
   - optionally a `get`-fetch for ids not present in the current option set.
   Chips must fall back to showing the raw id or "…" if the name is unknown — never crash.
3. **Duplicate ids** — dedupe `value` on toggle; never store duplicates in RHF field.
4. **Ordering / RTL chips** — chips should wrap and lay out RTL (`dir="rtl"` inherited from the trigger); cap the visible chips (e.g. show `N selected…` overflow) to avoid an oversized trigger.
5. **Cascade-clearing in parent-child chains** — this multi-select is used for **cross-cutting** relations (group↔classes), NOT for the strict Type→Class→Group→Model→Ware chain. The `clearFrom` cascade logic in `process-scope-fields.tsx` must **not** be applied to multi-select fields. Changing a WareGroup's classes does not invalidate downstream WareModels/Wares in the single-chain forms (they're linked to the group by id, not by class list).
6. **Fetching filter interplay** — when the admin first picks `wareTypeId`, the class fetcher should be filtered to classes of that type (mirror the process-scope-fields pattern: `...(values.wareTypeId ? { wareTypeId } : {})`). A group's classes are normally all under its `wareType`; enforcing this on the fetcher reduces invalid combos. The backend does **not** currently validate that `wareClassIds` all share the group's `wareType` — a data-integrity footgun to be aware of.
7. **Empty array vs. undefined** — decide one canonical "no selection" value. Backend treats `undefined` as "don't touch" (updateRelations) and empty array as "clear all" (because `replace: true` with `[]` unlinks everything). The form must distinguish "user cleared the field" (`[]`, should send) from "field untouched" (skip). In RHF, use `optional(array(...))` and only pass `wareClassIds` when the value is defined.
8. **`wareGroup.gets` multi-class visibility** — the admin list already shows all classes per group; a class filter (URL param `wareClassId`) will surface a group under every class it belongs to. No change needed, but test it once multi-select is live (a group with 2 classes must appear in both filtered lists).
9. **Store.wareTypes** — backend `store.updateRelations` now accepts `wareTypeIds` (array, `replace: true`) + `storeHeadId`/`cityId`/`stateId`. When wiring the same component into the store form, apply the identical patterns (array in `add`, full-set `updateRelations`, `replace: true`). Note `store.updateRelations` is also reachable by **StoreHead** (self-scoped by `_id`), so the store form can be offered to the store head to update their own relations.
10. **Type generation** — `wareGroup.add` / `wareGroup.updateRelations` `set` types come from `back/declarations` (regenerated by running `deno task bc-dev` with `typeGeneration: true`). The frontend `ReqType["main"]["wareGroup"]["add"]["set"]` already carries `wareClassIds?: string[]`. Confirm the generated types include it before coding against it (it should, since the validator declares it).
11. **Performance** — `wareClasses` reverse on WareClass has **no limit** and **no sort**; if a class ever gains thousands of groups, the embedded `wareGroups` array grows unbounded. Acceptable today; note it if scale becomes a concern.
